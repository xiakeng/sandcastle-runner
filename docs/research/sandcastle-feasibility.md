# Sandcastle feasibility for a Codex-only worktree runner

Research date: 2026-09-08. Scope: design research only; no runner implementation or real AI coding session was executed.

## Verdict

**Feasible as a TypeScript execution library, with lifecycle and parallel-host adaptations. No upstream fork is required merely to launch Codex, choose model/effort, pass an implement prompt, or stream output. Stock `noSandbox()` is insufficient if the runner must reliably identify process death, cancel a complete process tree, and prove that it is safe to finalize a worktree.** Its upstream ADR explicitly acknowledges leaked host processes on timeout/abort and forced completion. [Source](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/docs/adr/0019-completion-timeout-for-hanging-process.md#L14-L16)

For the intended ownership boundary, the runner should create/own each worktree and invoke `run()` with its absolute path as `cwd` and `branchStrategy: { type: "head" }`. This keeps Sandcastle from creating or removing that worktree and skips its merge step. Use a unique worktree, branch, and log path per concurrent invocation. [Head execution](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/SandboxFactory.ts#L342-L385), [merge bypass](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/run.ts#L736-L746)

## Material adaptations

### 1. Separate task completion from process termination

The default completion marker is `<promise>COMPLETE</promise>`. After observing a marker, Sandcastle can force a successful iteration after the completion idle grace period even if the process has not exited. With `noSandbox()`, teardown does not kill the process or its descendants. The upstream ADR explicitly records this leak. [Default marker selection](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/Orchestrator.ts#L330-L339), [grace timeout](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/Orchestrator.ts#L89-L114), [acknowledged leak](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/docs/adr/0019-completion-timeout-for-hanging-process.md#L14-L16)

For a process-exit-driven runner, `completionSignal: []` disables marker-triggered completion. This follows directly from the array assignment and `some`/`find` checks. It does not fix timeout/abort process leaks. A complete implementation needs a local provider or an external process supervisor that owns the process group, waits for terminal status, and kills remaining children before worktree finalization. [Signal handling](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/Orchestrator.ts#L174-L185), [signal list](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/Orchestrator.ts#L330-L339), [provider teardown](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/sandboxes/no-sandbox.ts#L164-L167)

There is a second exit-status problem: `noSandbox` receives only `code` in its child-process `close` handler and returns `exitCode: code ?? 0`. A signal-terminated child can therefore be represented as exit zero. This is a static source finding; no runtime reproduction was performed. A reliable provider should retain the terminating signal and treat unexpected signal termination as failure. [Close handlers](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/sandboxes/no-sandbox.ts#L110-L131)

The Codex stream parser recognizes `thread.started`, assistant messages, command starts, `error`, and `turn.completed` usage. It does not emit a normalized terminal turn-failure event. A runner needing `turn.failed` or exact native event semantics must parse `raw` itself and still wait for actual process exit. `RunResult` should be treated as execution evidence, followed by independent validation of expected commits, worktree status, and tests. [Parser](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/AgentProvider.ts#L699-L746)

### 2. Avoid concurrent writes to host Git global configuration

Every lifecycle performs `git config --global --add safe.directory` and, when configured, global `user.name` and `user.email` writes. Because the no-sandbox provider runs directly on the host, concurrent worktrees still share this mutable global file and can contend on its lock. The writes themselves are verified; the resulting race is a source-based inference, not a reproduced failure. [Lifecycle setup](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/SandboxLifecycle.ts#L211-L255)

A minimal downstream adaptation is a unique `GIT_CONFIG_GLOBAL` target in each provider's environment, initialized with the needed host configuration. Alternatively, change upstream to skip container-oriented Git-global setup for host execution. Merely giving each run a different worktree does not isolate this file. The provider accepts environment injection and merges it into spawned process environments. [Environment support](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/sandboxes/no-sandbox.ts#L24-L27), [environment merge](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/sandboxes/no-sandbox.ts#L45-L51)

### 3. Keep worktree ownership in one layer

If the runner owns creation, retry, and final cleanup, use top-level `run` in head mode against the existing worktree. Sandcastle's named-branch path creates/reuses managed worktrees and cleans them after runs; `createWorktree().close()` also removes clean worktrees. These APIs are valid alternatives only when their ownership behavior is desired. [Automatic cleanup](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/SandboxFactory.ts#L203-L225), [managed branch path](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/SandboxFactory.ts#L388-L447), [explicit close](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/createWorktree.ts#L260-L278)

## Configuration and documentation cautions

- Use `run`, not `interactive`, for automated workers. Codex's interactive argument builder only passes `--model` and the optional prompt; it ignores the provider's effort and approvals options. [Interactive builder](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/AgentProvider.ts#L816-L819)
- Prefer an inline prompt assembled by the runner. Inline prompts bypass prompt-file shell preprocessing. `promptFile` is resolved against `process.cwd()`, not the run's `cwd`, so use an absolute path if using files. [Prompt path](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/run.ts#L348-L356), [preprocessing](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/Orchestrator.ts#L406-L414)
- Some documentation is stale: the no-sandbox ADR says agent providers do not receive `dangerouslySkipPermissions: true`, but the current noninteractive orchestrator passes `true`, and Codex's builder unconditionally uses the bypass flag unless auto-review is selected. Base the runner contract on the inspected code. [Stale statement](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/docs/adr/0015-no-sandbox-in-run-and-create-sandbox.md#L24-L25), [actual invocation](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/Orchestrator.ts#L140-L146), [actual Codex flags](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/AgentProvider.ts#L794-L811)
- Codex session IDs are parsed from `thread.started`. Sandcastle's copy-to-host capture is gated on a bind-mount handle, so no-sandbox does not produce the same captured-session-file evidence as container runs; Codex runs directly against its host session storage. For CI repair, a fresh invocation does not require that capture mechanism. [Session ID parser](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/AgentProvider.ts#L704-L705), [capture gate](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/Orchestrator.ts#L502-L531)

## Does upstream need modification?

**Basic functional integration: no.** Current public API covers Codex-only host runs, model/effort, prompt transport, independent `cwd`, and raw stdout events.

**Reliable unattended execution: adaptation required.** Use an externally supervised worker process or a custom public provider implementation to own termination and signal status; isolate the Git-global configuration. Public provider interfaces are exported, so this can stay downstream rather than forking Sandcastle. Upstream fixes would improve the built-in provider but are not a prerequisite for a downstream adapter. [Public provider types](https://github.com/mattpocock/sandcastle/blob/e99f832f26dc9d245c019a9ddd19fa5dee792427/src/index.ts#L75-L105)

Since the proposed runner already owns worktrees, publication, CI, and retries, Sandcastle's remaining value is prompt/provider integration, streaming normalization, logs, and token/session metadata. A direct Codex process adapter is also a reasonable alternative if implementing a Sandcastle host-process adapter would duplicate most of that lifecycle. This is an architectural inference from the verified boundaries, not a performance benchmark or a recommendation based on a production trial.
